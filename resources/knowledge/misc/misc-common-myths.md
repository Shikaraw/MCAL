## 症状

- 反复重装游戏、反复加内存却解决不了崩溃；
- 听传言删了 `crash-reports`、关了日志，问题依旧；
- 装了五六个「优化」模组后反而更卡；
- 把 `-Xmx` 调到物理内存的 90% 后游戏启动更慢。

## 原因

以下误区广泛流传，根源是把「某个场景下的经验」当成普遍规律：

1. **「内存越大越流畅」**：`-Xmx` 只影响 GC 与区块缓存；过大堆会让单次 GC 停顿变长，且可能触发系统换页。适量（一般 4–8G，大型整合包 8–12G）即可。
2. **「优化模组越多越好」**：多个渲染核心（Sodium/Embeddium/OptiFine）或同功能光照模组互斥，叠加只会崩或更慢。每类只装一个。
3. **「Java 越新越好」**：1.16.5 及更老的模组用 Java 8 才稳定；新 Java 反而报 `Unsupported class file major version` 的另一种形态或直接不兼容老 Forge。
4. **「卸载重装能解决一切」**：重装只清除你下载的文件，不改变配置习惯；不看日志永远找不到根因（`logs/latest.log` 与 `crash-reports/` 才是答案）。
5. **「FPS 越高越好，必须关垂直同步」**：不限帧让 GPU 持续满载，笔记本更快降频、台式机更耗电；限帧到刷新率或开自适应同步体验更稳。
6. **「Invalid session 是被封号」**：它几乎总是 token 过期、网络或时间偏差导致，重新登录即可；封号有明确的提示与申诉渠道。
7. **「正版账号可以多人共享」**：违反 EULA，且多人同时登录会互相踢下线；共享黑卡账号还有被盗与被封风险。
8. **「模组丢进 mods 就能用」**：还需要匹配游戏版本、加载器、前置依赖与 Java 版本；缺一不可。
9. **「32 位 Java 也能分配 4G 内存」**：32 位 JVM 堆上限约 1.5G，写再大也会报 `Could not reserve enough space for object heap`；必须换 64 位。
10. **「删掉崩溃报告就没事了」**：那是唯一的证据链；正确做法是保留并据此定位。

## 解决方案

1. 遇到问题按固定流程走：**看日志（latest.log / crash-reports）→ 按报错文本检索知识库 → 一次只改一个变量 → 复测**。
2. 调参前记录当前状态（版本、加载器、模组数量、`-Xmx`、Java 版本、驱动版本），改完对比；这样即使失败也能回退。
3. 内存与 GC 参数照抄经过验证的方案（见 [[java-memory-flags]]），不要叠加「偏方」。
4. 优化只保留一套组合（见 [[mod-performance-stack]]），其余用设置与硬件解决。
5. 装模组遵循「版本 → 加载器 → 前置 → 依赖范围」四步核对。
6. 账号只自己用；需要多人玩同一个游戏就开服务器（见 [[server-setup]]），而不是共享账号。
7. 对任何「删文件/改注册表/关杀毒」类建议，先问依据；能用日志证明的才执行。

## 验证

按上述准则处理后：同类问题不再复发；调整参数前后有可对比的日志/帧率记录；不再出现「重装后又崩」的循环。
